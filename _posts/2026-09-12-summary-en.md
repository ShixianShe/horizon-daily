## [210M text-to-image DiT trained from scratch on a single GPU](https://www.reddit.com/r/MachineLearning/comments/1wdfmvq/training_a_210m_texttoimage_dit_from_scratch_on/) ⭐️ 8.0/10

A developer trained a 210M-parameter text-to-image diffusion transformer from scratch on a single RTX PRO 6000 GPU over 3.5 days, using 4.2M images at 256² resolution. The run produced three measurements: learned null attention slots absorb ~90% of cross-attention mass at mid-noise, flow-matching loss tracks training health rather than sample quality, and a training-time timestep shift of 2.8 outperforms doubling sampling steps. This provides rare, plainly stated empirical evidence about attention-sink behavior and loss interpretation in text-to-image diffusion transformers, which are usually trained at industrial scale and rarely documented at this level of detail. Practitioners working on small-scale diffusion training, register tokens, or flow-matching objectives can use these findings to guide architecture and training decisions. The model uses a cross-attention DiT (896 width, 16 blocks) with 2D RoPE, QK-norm, SwiGLU, and adaLN-single, plus 16 register tokens and 2 learned key/value slots; register vectors grow to 4–13× the norm of image tokens by middle blocks. Held-out FID improved from 33.7 to 27.0 while flow-matching loss only moved from 0.805 to 0.754, and the shift of 2.8 derives from the SD3/RAE rule for the 32-channel FLUX.2 latent.

reddit · r/MachineLearning · /u/IvanMikhnenkov · Sep 11, 13:00

**Background**: Diffusion transformers (DiTs) replace the U-Net backbone of latent diffusion models with a transformer operating on latent patches, enabling scalable text-to-image generation. Register tokens are extra tokens added to a transformer's input to absorb excess attention, preventing normal tokens from becoming 'attention sinks' that distort feature representations. Flow matching is a training objective that learns a velocity field transporting noise to data, and its loss is often assumed to correlate with sample quality.

## [OpenRouter's automatic provider routing can silently change model behavior](https://simonwillison.net/2026/Sep/11/so-you-want-to-use-openrouter/) ⭐️ 7.0/10

Mohamed Moustafa, amplified by Simon Willison, warns that OpenRouter's automatic provider routing can serve the same model ID from backends running different serving software, optimizations, and settings, so responses may behave inconsistently. Concrete examples include providers lacking vision capability for vision models and differing handling of the reasoning effort option, with provider.only offered as the workaround. Developers building on multi-provider LLM APIs may see non-reproducible outputs, missing capabilities, or shifting costs without changing any code, which undermines evaluation, debugging, and production reliability. This is a practical caveat for anyone treating OpenRouter as a single stable endpoint rather than a routing layer over heterogeneous backends. The provider.only option lets you restrict routing to specific providers, and the /endpoints method returns the list of available providers for a given model ID. Note that using a base provider slug such as "google-vertex" in routing fields matches all endpoints for that provider, including variants and regions.

rss · Simon Willison · Sep 11, 22:49

**Background**: OpenRouter is a unified API gateway that lets you call many LLM models through one endpoint, advertising automatic fallbacks and cost-effective provider selection. Behind a single model ID, different providers may run different serving stacks such as vLLM or TGI with their own batching, quantization, and feature flags, so the same model can behave differently depending on who serves it.

## [Simon Willison Urges Developers Not to Sleep on Wrapture](https://simonwillison.net/2026/Sep/11/wrapture/) ⭐️ 7.0/10

Simon Willison published a blog post on September 11, 2026, recommending wrapture, a new Python monkey patching library by Graham Dumpleton, noting that it has seen surprisingly little buzz despite rapid development since its August 31 release. Dumpleton has been publishing near-daily tutorials covering unit testing, call recording, phased behavior, live and zero-code tracing, Flask instrumentation, slow-code detection, and OpenTelemetry export. Wrapture combines monkey patching for testing with observability-style tracing in a single library, potentially replacing or complementing tools like unittest.mock and New Relic-style APM agents. If it matures, it could become a Swiss Army Knife utility that Python developers rely on for years across testing, debugging, and production tracing. Wrapture is still alpha software, but it is already usable, especially because tracing can be configured via a separate TOML file without modifying any Python code. A companion package, wrapture-instrumentation, provides instrumentation for a wide range of libraries including Flask, Django, FastAPI, aiohttp, gRPC, httpx, requests, SQLAlchemy, sqlite3, Starlette, urllib3, and uvicorn, and there is also a set of interactive JupyterLab workshops.

rss · Simon Willison · Sep 11, 13:51

**Background**: Monkey patching is a technique in dynamic languages like Python for modifying or extending the behavior of classes, modules, or functions at runtime, and it is commonly used in testing to replace real functions with mocks. Graham Dumpleton is a well-known Python developer, creator of mod_wsgi and the wrapt library, and wrapture is built on the idea of attaching bindings to arbitrary call sites without modifying the observed code. Observability tools such as New Relic and OpenTelemetry typically trace how requests flow through an application to help diagnose performance and behavior issues.
